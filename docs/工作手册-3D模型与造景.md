### 3. 造景系统闭环

上一轮已落地、本轮验证并补完的链路：

```
index.html  #scapeOptions
  → app.js  [data-scape] click → SIM.applyScape(state, id) → R.rebuild(state) → save()
  → sim.js  SCAPES 四套模板（三峰式 / 岛式 / 斜线式 / 平原式）+ random
```

新增能力：
- `render.js` 的 `ROCK_GLB = {pebble, angular, slate}` 映射到 3 个 GLB；模型未到位时自动回退 `makeRockStyled()`，首屏不会空石头位。

## 二、关键踩坑（按重要性排序）

### 1. GLB 与缩略图都必须带版本号，否则浏览器吃旧缓存

现象：把水榕 GLB 里的砂盘裁掉、文件也替换了，浏览器里两块白色圆盘还在。

根因：`glbLoader.load('models/' + sp.model.file, ...)` 和 `img.src = 'models/thumbs/xxx.png'` 都是裸 URL，Chrome 一直用缓存的旧资源；换页面 `?v=` 不影响子资源。

修复：两处都追加 `?v= + window.AW_MODEL_VER`（`build-models.js` 每次重建会刷新该时间戳）。这是产品级修复 —— 以后换任何模型/图标都会自动生效。

### 2. 砂盘底座必须改几何，不能靠渲染时下沉

第一版做法：`model.baseCut` 把整株下移一点，让 AI 生成模型自带的砂质圆盘沉到砂面下。
失败原因：`syncCreatures()` 会按生长比例做 `g.scale.set(.55+r*.5, r, .55+r*.5)`，幼株时下沉量被一起缩小，圆盘又冒出来。

正确做法：新增 `tools/trim_decor_base.py`，按几何删除「整片三角形都落在底座切片内」的面。
AI 摆件是 Z-up，底座在 `z=maxZ`（约 0），植株朝 -Z 生长；判定 `min(z_a,z_b,z_c) > maxZ - span*cut` 才删，不会误伤根部。
- `anubias.glb`：删 9295/40000 面，剩 30705 面；
- `hornwort.glb`：删 4255/39997 面，剩 35742 面。

`baseCut` 仍保留为可选参数（默认 0），供以后未裁剪的摆件临时使用。

### 3. AI 摆件是 Z-up，渲染前必须扶正

诊断 bbox：金鱼藻 `z[-1.104, 0]`、水榕 `z[-0.790, 0]` —— 长轴在 -Z，而 three 场景是 Y-up。
`buildGlbPlant()` 原先按 `size.y` 归一化，会把水草放倒。

修复：用独立 `fix` 层绕 X 轴 `+π/2`（`y' = -z`）扶正，**不能改 GLB 根节点自带的旋转**；`model.axis` 可显式指定 `y/z/x`，缺省按包围盒最长轴推断。
注意「最长轴推断」对矮而横铺的水草会误判（moss / duckweed），所以参数化水草在 `species.js` 里一律显式写 `axis: 'y'`。

### 4. 极扁模型按高度归一化会放大几十倍

浮萍厚度只有 0.009，按 `k = full / size.y` 会放大约 78 倍变成巨盘。
修复：`sp.floating || sp.shape === 'float'` 时改用 `Math.max(size.x, size.z)` 作参考轴，并跳过 `baseCut`。

### 5. 离线缩略图要按模型轴向/视角分别渲染

`quick_render.py` 默认看 XY 平面（Z 为深度），拍 Z-up 摆件只能拍到横截面。新增环境变量：
- `QR_AXIS=z`：把 `(x,y,z) → (x,-z,y)`，摆件扶正；
- `QR_VIEW=top`：同样变换，用于俯视浮萍；
- `QR_CUT`：按高度跳过底座切片内的三角形（砂盘已从几何删除后不再需要）。

`make_thumbs.py` 用 `VIEW_OF` 按文件配置这些参数。

### 6. `recolor_glb.py` 重建 GLB 时必须重排 bufferView

贴图重新编码后长度会变，必须重建 BIN chunk 并同步修正所有 `bufferView.byteOffset` / `byteLength` / `buffers[0].byteLength`，否则 accessor 全部越界。

### 7. 手写 glTF 的固定要点

- 每个 bufferView 都要带 `buffer: 0`；
- 4 字节对齐；`buffers[0].byteLength` 取补齐后的长度；
- POSITION accessor 必须写 `min`/`max`；
- `doubleSided: true`（叶片是单面条带）；
- 退化面的法线给安全值，不能留 `(0,0,0)`，否则光照出 NaN。

### 3. 本轮修掉的一个隐性 bug：重复 `model` 字段

`tools/ingest.py` 原来用「`id` 到 `look` 之间有没有 `model`」判断字段是否存在。但 `tools/attach_models.py` 是把 `model` 插在 `look` **之后**的，于是写实鱼接入时判定为「没有」，又写了一遍。JS 里后一个 `model` 静默覆盖前一个，不报错但会悄悄丢掉手调参数（如 `axis` / `yaw`）。

修复：`ingest.py` 改为复用 `ingest_decor.patch_species()`（它扫描整个品种对象，替换或插入都正确）：

```python
import importlib.util
_sp = importlib.util.spec_from_file_location(
    'ingest_decor', os.path.join(TOOLS, 'ingest_decor.py'))
_dec = importlib.util.module_from_spec(_sp)
_sp.loader.exec_module(_dec)
print('   ✓ %s model 字段' % _dec.patch_species(sid, out_name))
```

并清掉 `species.js` 里 `goldfish` / `neon` 的重复行。复核方式：`Grep` 统计 `^\s*id: '` 与 `model: {` 均为 38，一一对应。

## 七、迭代三十一：鱼体真实比例与 90cm 默认缸

用户诉求：`鱼的尺寸在缸内显示的比例不正确，偏大了一些，同时将默认缸的大小调整为90cm`。

### 1. 根因：`PXCM` 写死，与缸宽无关

`render.js` 里 `var PXCM = 0.42`（1cm 对应的 3D 单位）是个全局常量，而缸的标称厘米数只写在 `species.js` 的 `desc` 文案里，代码完全不知道缸有几厘米。于是鱼按 `sizeCm * 0.42` 渲染，缸却按 `TANK.w` 变化 —— 缸越大，鱼相对缸越偏大：

| 缸 | 标称 cm | `TANK.w` | 正确的 `w/cm` | 旧版 0.42 偏大 |
| --- | --- | --- | --- | --- |
| 迷你缸 | 30 | 12.0 | 0.400 | +5% |
| 标准缸 | 45 | 16.8 | 0.373 | +13% |
| 大缸 | 60 | 21.0 | 0.350 | +20% |
| 落地缸 | 90 | 25.5 | 0.283 | **+48%** |

修复：给 `tankSizes` 每项加显式 `cm` 字段，`applyDims()` 里按 `PXCM = (TANK.w / t.cm) * FISH_VIS` 动态计算。这样任意缸都满足「鱼占缸宽比例 = sizeCm / cm」。`FISH_VIS` 默认 1.0（严格真实比例），嫌鱼在画面里太小可调到 1.15~1.25，四档缸等比放大、不破坏缸间比例。

顺带修掉同类硬编码：`app.js` 里水草株高用 `c.h * 45` / `sp.maxH * 45` 换算成厘米，45 是旧默认缸宽。改成 `tankCmH()`：`1 个 3D 单位 = cm/w 厘米`，缸高 `h` 个单位即 `cm * h / w` 厘米，与渲染层 `sp.maxH * TANK.h` 精确对齐。

### 2. 默认 90cm 缸 + 存档一次性迁移

- `sim.js:create()` 的 `tankSize` 改为 `'huge'`（现有 90cm 落地缸档），`species.js` 把「默认配置」文案从 medium 挪到 huge。
- `sanitize()` 增加 `tankMig` 标记：旧存档显式存着 `medium`（旧默认值）或缺字段的，升级为 `huge`；主动选过 `small` / `large` / `huge` 的保持原样；迁移只做一次，之后玩家主动换缸不会被覆盖。六个分支都跑过用例。
- 不迁移的话，本地已有存档打开页面仍是 45cm 缸，用户会以为改动没生效 —— 这一步不能省。

### 3. 副作用：大缸 90 天全缸死于氨氮过高

改默认缸后跑长周期模拟，`huge` 缸 90 天鱼数归零，死因全是「氨氮过高」；对照 `medium` 缸 120 天仍有 16 条鱼。

根因是模拟层一个既有物理缺陷：`capacityOf()` 按 `tank.cap` 放大（huge = 2.1 倍），繁殖封顶随之放宽，但氨氮 / 硝化动力学**完全不随水量缩放** —— 大缸养了 2 倍鱼，排泄污染却按小缸算。

修复：新增 `waterFactor(s)`，按缸体几何体积相对 45cm 基准缸换算，把「浓度」类增量都除以它：

```js
function waterFactor(s) {
  var t = D.tank(s.tankSize);
  return clamp((t.w * t.h * t.d) / (16.8 * 8.4 * 6.2), 1.0, 3.2);
}
```

作用于四处：`waste`（氨氮来源）、水草吸收硝酸盐、鱼呼吸耗氧 `oxyUse`、死亡时的污染脉冲。硝化能力**不缩放**（过滤器/硝化菌按设备算，大缸配得上更大过滤）。

**`clamp` 下限必须是 1.0**：第一版给了 0.5，30cm 小缸污染被放大一倍，实测 60 天全缸死亡 —— 用「临时替换 waterFactor 为 return 1」的对照脚本确认是我引入的回归后改掉。现在只让比标准缸大的缸拿到稀释收益，小缸手感完全不变。

### 1. 排查顺序（别急着改材质）

这 5 个品种恰好都是**参数化鱼**（`tools/gen-fish-models.js` 产出，60–90 KB），而写实 AI 鱼正常。逐层排除：

| 检查项 | 结果 |
| --- | --- |
| GLB 结构 / accessor 越界 / NaN | 全部正常 |
| `baseColorTexture` 内嵌贴图 | **鲜艳正常**（斗鱼玫红、锦鲤白底红斑、宝莲灯蓝红带） |
| 材质 `baseColorFactor` / `metallic` / `roughness` | 正常 |
| `COLOR_0` 顶点色 | 平均 0.92，无黑顶点 |
| `glbLookOf()` 色型重映射 | 只对 `variantOf` 生效，这 5 个是基础品种，不走 |
| **NORMAL 法线** | **313/473 = 66% 是零向量 `(0,0,0)`** ← 根因 |

写实模型法线长度全是 1.0。Three.js 里 `normalize(vec3(0))` 得到 NaN / 零，`dot(N,L)` 归零，漫反射全无 → **WebGL 里纯黑**。离线软件光栅化器 `quick_render.py` 有 NaN 兜底（退化平光 0.72），所以静态图标只是明显偏暗，不是全黑 —— 这个差异是定位的关键线索。

全量扫描确认 **16 个模型**受影响（15 个参数化鱼 + 历史资产 `betta_procedural.glb`），水草 / 石头 / 螺不受影响（`gen_decor_glb.py` 的法线是对的）。

### 2. 根因：`mergeGeo()` 顶点索引被重复乘 3

```js
// tools/gen-fish-models.js 旧代码
const a = p.idx[i] * 3;                       // a/b/c 已是 float 数组偏移
[a, b, c].forEach(v => nor2[v * 3] += ...);   // 又乘 3 → 索引放大 9 倍
```

`Float32Array` 越界写入被静默丢弃，绝大多数累加丢失，只有极少数碰巧落在范围内的被写入。于是 2/3 顶点法线留在 0。

修复：`ia/ib/ic` 保留**顶点索引**用于累加，`a/b/c` 只用于叉积取坐标；孤立顶点（无三角形引用）给 `(0,0,1)` 兜底，避免任何路径算出 NaN。

同时给生成器加 `AI_REPLACED = new Set(['neon','goldfish'])` 跳过列表 —— 这两个品种已换成 2.2 MB 的 AI 写实模型，**重跑生成器会覆盖它们**，加 `--all` 才能强制生成参数化版本。

### 2. 金鱼藻躺倒：根因是「扶正了两次」

现象：缸里金鱼藻横躺，水榕也偏倒。

排查链：

1. `species.js` 声明 `model: { file: 'hornwort.glb', axis: 'z' }`；
2. 读 accessor 的 POSITION min/max：hornwort 尺寸 `X 0.53 / Y 0.542 / Z 1.104`，长轴确实在 Z —— 声明看起来没错；
3. **但 GLB 的 `node[0]` 带 `rotation = [0.7071, 0, 0, 0.7071]`**，即绕 X +90° 的四元数。也就是说模型加载后已经是 Y-up；
4. `buildGlbPlant()` 拿到 bbox 后又按 `axis:'z'` 转了 ±90° → **多转一次 → 躺平**。

`anubias.glb` 同一个 root 旋转，同一类问题（它是矮丛，躺着不如金鱼藻明显）。

- `render.js:buildGlbPlant()` 加**运行时轴向校验**：声明轴必须真的是当前最长轴（容差 0.98）才扶正，否则按 `y` 不转。这样以后接入任何自带 root 旋转的模型都不会双转。
- `species.js` 把 `anubias` / `hornwort` 的 `axis` 从 `'z'` 改成 `'y'`（模型自带朝向已经正确，显式声明不扶正）。

**反证验证**：临时把 hornwort 的声明改回 `'z'`，门禁立刻输出
`✗ hornwort 声明=z 实际=z 世界 0.530/0.542/1.104 躺倒!`，改回 `'y'` 后恢复 `✓ ... 立着`。说明门禁真的能抓，不是摆设。

用户：`皇冠草为什么是趴在地上的`。

### 1. 先排除模型问题

图鉴展示台里皇冠草**是立着的**（莲座状、叶片向上），顶点世界 Y 分布也正常（中位数 0.35、最高 0.98，三轴 0.958/0.980/0.909）。所以不是模型朝向问题——是**缸内渲染**把它压扁了。

### 2. 根因

`render.js:syncCreatures()` 里水草缩放：

```js
// 旧
var yCap = Math.min(1, (WATER_Y - 0.06 - (terrain.top(px) - BASE_Y)) /
  Math.max(.001, sp.maxH * TANK.h));
g.scale.set(.55 + r * .5, r * yCap, .55 + r * .5);
```

`terrain.top()` 返回的是**世界坐标**（`BASE_Y + 砂面`，约 -4.2），代码又减了一次 `BASE_Y`，分子变成「砂面厚度」约 0.5，而不是「砂面到水面」的 9.12。

结果 90cm 缸里 `yCap = 4.42 / 6.448 = 0.686`：**纵向被压掉 31%，横向却是 1.05 倍**——宽高比凭空拉伸 1.5 倍，宽叶莲座直接趴在地上。

加重因素：横向下限 `0.55 + r*0.5` 太高，幼株（r≈0.3）横向还有 0.70，纵向只有 0.21，扁得更明显。

### 3. 修复

```js
var availH = WATER_Y - 0.06 - terrain.top(px);          // 砂面到水面的真实可用高度
var yCap = Math.min(1, availH / Math.max(.001, sp.maxH * TANK.h));
var gx = Math.max(.30, r * 1.05);                        // 横竖接近等比
var gy = Math.max(.26, r * yCap);                        // 幼株小一号，但不趴
g.scale.set(gx, gy, gx);
```

- 成熟时：`gx = 1.05`、`gy = 1.0`，宽高比回到模型本身的比例。
- `yCap` 仍然防穿顶：hornwort `maxH 0.92` → `full 9.568`，`yCap = 9.12/9.568 = 0.953`，顶部 4.92 < 水面 4.98，正好不冒头。
- 幼株：`r=0.06` 时 `gx 0.30 / gy 0.26`，接近等比的小丛，不再是"横向铺开、竖向极矮"的扁片。

### 4. 验证

实机买一株皇冠草入缸：叶片向上展开成莲座，不再贴地；水榕、蜈蚣草、莫斯同步变高，全部在水面以下。门禁 10 节全绿，版本 `20261116w → x`。

**教训**：只要看到「水草矮扁/趴地」，先查两件事——`axis` 是否双转（root 旋转）、`yCap` 这类高度上限换算是否把坐标系搞混。这两处都会让同一株草在缸里和图鉴里长得完全不一样。

## 十四、螺虾行为修复（螺漂浮 + 虾活动与腿）

用户报告：`1.虾的活动不正常，且脚不会动；2.螺不应该漂浮在水中`。

### 1. 根因

三处叠在一起：

| 现象 | 根因 |
| --- | --- |
| 螺漂浮在水中 | `sim.js` 的漫游逻辑用 `sp.layer[0]/[1]` 算垂直边界，而 4 种螺虾（`kind: 'invert'`）**都没有 `layer` 字段** → `undefined - 0.05 = NaN` → 边界失效 → 最终被 `finite(c.y, 0.6)` 兜到**中层** |
| 第二处漂浮来源 | 螺虾专属的「爬向」逻辑里写死 `wall = 0.86 + sin(...) * 0.07`，等于让螺在离缸底 17% 的位置上下浮 |
| 初始位置越界 | `createCreature` 里虾的初始 y 写死 `rnd(0.68, 0.93)`，比它自己的层位下沿 0.76 还低，出生就在层外 |
| 脚不会动 | `shrimp.glb` 是**纯静态网格**（骨骼 0 / 动画 0，47375 顶点），腿是死几何。`buildGlbFish` 只挂整体变换，没有任何骨骼动画 |

另外 `buildInvert` 第一行是 `if (sp.model && glbModels[sp.model.file]) return buildGlbFish(sp)`——螺虾都有 GLB，所以程序化模型里那段「触须抖动」（`antGroup`）从来没对它们生效过。

### 2. 改法

**① `js/species.js`：补齐 `layer`**

| 品种 | layer |
| --- | --- |
| 苹果螺 / 神秘螺 / 斑马螺 | `[0.88, 0.96]`（贴缸底） |
| 黑壳虾 | `[0.76, 0.95]`（底层活动） |

**② `js/sim.js`：三处收紧**

- 初始 y 改为从 `layer` 推导（`rnd(layer[0]+0.01, layer[1]-0.01)`），不再是写死的区间
- 垂直边界对 invert 收紧：`lo = max(lo, layer[0]-0.03)`、`hi = min(0.962, layer[1]+0.02)`；虾在 `dart` 状态下 hi 放宽 0.12（保留弹跳）
- 垂直速度对 invert 衰减到 `×0.12`（虾 dart 时 ×0.9），并把「爬向」的 `wall` 从写死的 0.86±0.07 改成按 layer 推：螺 `layer[1]-0.02 ± 0.012`、虾 `layer[0]+0.12 ± 0.04`

**③ `js/render.js`：顶点着色器驱动摆动**

GLB 没有骨骼，改不了腿，于是在渲染期用顶点位移做：

```glsl
float legMask = smoothstep(0.16, -0.10, transformed.z);   // 腹部一侧
float wph = uTime * (uAmp > 0.02 ? 8.0 : 1.6) + transformed.x * 7.0;
transformed.z += sin(wph) * uAmp * legMask;
transformed.y += cos(wph * 0.9) * uAmp * 0.55 * legMask;
```

虾 `uAmp = 0.030`（快、腿区摆动明显），螺 `uAmp = 0.008`（极缓的呼吸）。`uTime` 在动画循环里更新。因为 `onBeforeCompile` 要首帧才触发，shader 引用用**数组引用**传给 `g.userData.waveShaders`，之后 push 进来的 uniform 就能被循环拿到。

### 3. 门禁：`tools/verify_inverts.js`（已接入 `verify_assets.js` 第【9】节）

- 4 种螺虾的 `layer` 必须完整合法
- 每种买 4 只，初始 y 落在层位内
- 跑 2400 步（240 秒）模拟，全程无 NaN，且 y 不得低于层位下沿（螺容差 0.02、虾 0.05）

### 4. 实测

| 品种 | y 范围（240 秒模拟） | 层位 |
| --- | --- | --- |
| 苹果螺 | 0.899 – 0.952 | 0.88 – 0.96 |
| 神秘螺 | 0.918 – 0.952 | 0.88 – 0.96 |
| 斑马螺 | 0.905 – 0.952 | 0.88 – 0.96 |
| 黑壳虾 | 0.786 – 0.919 | 0.76 – 0.95 |

缸底约在 0.955，螺的 y 稳定在 0.9–0.95，**贴住缸底**。实机确认水体中部只有鱼、没有漂浮的螺。

### 5. 遗留

- **虾腿是 shader 近似，不是真骨骼**。腿会随身体轻微摆动，但不会做出「步足交替扒地」那种精确动作。要真做到，得给 `shrimp.glb` 在 Blender 里绑一组腿骨 + 权重，属于独立工作量。
- 商店面板的「收起」按钮偶发点不中（坐标命中但面板不关），不在本次范围。

## 十五、自定义缸体尺寸（长宽高）

用户需求：`缸体尺寸修改为自定义长宽高，长最小值为30cm，最大值为200cm，高度和宽度也可以调整`。

### 1. 关键决策：统一尺度

旧的四档预设比例其实**互不一致**：

| 预设 | 标称长 | 3D 宽 | cm/单位 |
| --- | --- | --- | --- |
| 迷你缸 | 30cm | 12.0 | 0.400 |
| 标准缸 | 45cm | 16.8 | 0.373 |
| 大缸 | 60cm | 21.0 | 0.350 |
| 落地缸 | 90cm | 25.5 | 0.283 |

同一只 5cm 鱼在不同缸里占宽比例并不守恒。改成手填长宽高之后必须统一尺度，否则同一个「30cm 缸」换成自定义值会突然变形。

**基准取「90cm 落地缸 = 25.5 单位宽」，即 `CM_PER_UNIT = 90 / 25.5 ≈ 3.529`**。

```js
function tankFromCm(l, w, h) {
  l → [30,200]，w/h → [20,80]
  w: l / CM_PER_UNIT,  h: h / CM_PER_UNIT,  d: w / CM_PER_UNIT
  cap: min(5, max(0.35, 2.1 * (V / V90) ** 0.55))
}
```

**容量用 0.55 次方而不是线性**：线性的话 200cm 缸的负载上限会是 90cm 的 12 倍，过滤根本跟不上；0.55 次方让大缸确实更省心，但不至于无脑塞鱼（200cm 缸 cap 封顶 5.0）。

**水量系数上限从 3.2 放到 10**：200cm 缸水量是 90cm 的十倍以上，压在 3.2 会让大缸污染物浓度被算高十倍。

### 2. 改动清单

| 文件 | 改动 |
| --- | --- |
| `js/species.js` | 新增 `CM_PER_UNIT`、`TANK_LIMITS`、`tankFromCm()`、`mapTank()`；`D.tank(spec)` 现在支持 `{l,w,h}` / state / 预设 id 三种入参 |
| `js/sim.js` | `create()` 加 `tankDims: {l:90,w:30,h:37}`；`sanitize()` 加迁移与越界夹取；新增 `setTankDims()`，`setTankSize()` 保留但内部转成自定义尺寸；5 处 `D.tank(s.tankSize)` 改 `D.tank(s)` |
| `js/render.js` | `applyDims()` 改传 state |
| `js/app.js` | `renderSettings()` 改成三个滑块的读写；删掉预设卡片点击；新增 `applyTankDims()` |
| `index.html` | 预设按钮换成三行「标签 + range + 数值 + cm」 |
| `style.css` | `.tank-dims` / `.tank-row` / `.tank-val` 等滑块样式 |

**交互细节**：滑块 `input` 只更新数字显示，`change`（松手）才真正换缸——否则每拖一格都 rebuild 一次场景会卡。

### 3. 存档兼容

## 十六、「缸内太挤了」误报（大缸买不进东西）

用户反馈：`为什么会提示"缸内太挤了"，明明是大缸`。

### 1. 根因：写死 48，而且把水草算进去了

`sim.js:181` 原来是：

```js
if (s.creatures.length >= 48) return { ok: false, msg: '缸里太挤了，先分一些成员出去吧' };
```

两个问题叠在一起：

1. **`s.creatures` 里包含全部水草**——缸里种一片草就能把名额吃光；
2. **48 是写死的，与缸体大小完全无关**——136cm 缸和 30cm 缸一个待遇。

复现：25 条鱼 + 23 株草（含初始生物）到 48，之后**连水草都买不进**。

### 2. 第二处同类问题：大型鱼门槛

```js
if (sp.bioload >= 3 && capacity < 17) ...   // 大型鱼
```

`capacity` 是 `capacityOf(s)`，90cm 缸加满过滤也只有 13 左右，**永远达不到 17**，等于「大缸也养不了锦鲤」。

### 3. 改法

**头数上限**：只数活体（鱼 / 螺虾），并按缸体容量缩放：

```js
var animals = 0;
for (...) { var asp = D.get(s.creatures[ai].specId); if (asp && asp.kind !== 'plant') animals++; }
var headCap = Math.round(clamp(13 * D.tank(s).cap, 12, 80));
if (animals >= headCap) return { ok: false, msg: '缸里太挤了（' + animals + '/' + headCap + '），…' };
```

提示里带上 `当前/上限`，用户一眼能看出差多少。

**大型鱼门槛**：改成「缸够大 **或** 负载余量够」两条路都留：

```js
if (sp.bioload >= 3 && D.tank(s).cap < 1.8 && capacity < 20) ...
```

（先改成只判 `cap`，会把「加装过滤」这条路堵死、提示文案也自相矛盾，所以保留 `capacity >= 20` 作为第二通道。）

### 4. 实测

| 缸体 | cap | 水草 | 活体上限 |
| --- | --- | --- | --- |
| 90cm | 2.1 | 40 株 | 27 |
| 136cm | 2.54 | 40 株 | 34 |
| 200cm | 5.0 | 40 株 | 42（先被生物负载拦住，不是头数） |

- 水草 40 株全部种得进，不占名额；
- 136cm 缸能买锦鲤，45cm 缸会被拦并给出明确原因；
- 实机：136cm 缸连买 4 株水榕，居民数 23 → 27，**没有弹「太挤」**。

### 5. 门禁

`verify_assets.js` 新增第【10】节：水草不占名额、活体上限随缸递增、大缸放行大型鱼 / 小缸拦住。

### 6. 备注：居民数包含水草

顶部「N 位居民」用的是 `state.creatures.length`，**水草也在内**。这与「居民」面板一致（面板里水草按「株高 XXcm」单列一条），数字和列表条数自洽，所以没改口径。如果希望顶部只显示活体数量，需要同时决定面板是否过滤，属于产品口径问题。

## 十七、水草写实模型返工 + 缓存版本串（11-17 下午）

### 1. 触发

上午的 5 个写实模型只看了「面数达标」，没看**形态**。实机一看就露馅：三角莫斯是一坨光滑的瘤状团块，蜈蚣草是一丛矮灌木。

### 2. 两个形态翻车与 prompt 修正

| 品种 | 症状 | prompt 修正 |
| --- | --- | --- |
| 三角莫斯 | 光滑团块 + 稀疏尖刺，像多肉 | 加 `fine feathery branching threads / fuzzy textured / no smooth blobs / no large smooth lumps` |
| 蜈蚣草 | 矮灌木丛，但 `maxH = 0.86` → 满高约 32cm，会变成巨型灌木 | 加 `single tall stem / one long slender vertical stem / whorls of small narrow leaves along its entire length` |

结论：**AI 文生 3D 对「团块类」品类会退化成光滑体块**（苔藓、藻垫、珊瑚），prompt 必须显式否定 `smooth blobs/lumps`；**对「单茎/单枝」品类必须写 `single stem`**，否则默认给灌木丛。

### 3. 新工具 `tools/trim_plant_base.py`

`trim_decor_base.py` 是「按固定比例切底部 9%」，对细长水草连根带茎一起切。新工具按特征识别底座盘：

```
盘层 = 半径≈全模型最大半径 + 厚度只有总高百分之几 + 顶点极密
盘厚上限 = 总高 3.5%（用 8% 会把莫斯团块误判成盘，一刀砍掉 24% 的面）
两端都试（AI 产物有时 Z-up、有时根节点已带 +90° 旋转），取更像盘的一端
```

实测：牛毛毡盘厚 1.53%、删 5388 面；皇冠草 / 蜈蚣草 / 莫斯全部判为「未识别到底座盘」→ 原样输出（皇冠草的盆比叶展窄，藏在叶下，不需要处理）。

> 顺带纠正一个误判：**「裁剪后顶点数没变」不等于没裁剪**——trim 只改 indices（删面），顶点缓冲原样保留。要靠面数判断。

### 4. 缩略图：Z-up 模型必须扶正

`tools/make_thumbs.py` 的 `VIEW_OF` 缺新水草配置，默认视角把 Z-up 模型拍成**俯视截面**：蜈蚣草成一朵正面莲座、莫斯只剩砂盘、牛毛毡是一团绿糊。补 `sword / hairgrass / moss / elodea → QR_AXIS='z'` 后图标才认得出。

### 5. 最容易白干的一步：模型缓存版本串

